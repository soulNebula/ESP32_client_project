# 系统架构与实现说明 —— ESP32-S3 智能家居

> 这份只讲**代码是怎么串起来的**。接线看 [`接线文档.md`](接线文档.md)，手机端接口看 [`MQTT协议.md`](MQTT协议.md)。

## 一、四个包，各管一摊

```text
main  ──>  BSP / App / ui    唯一认识所有人的地方，board.c 在这里按顺序初始化
App   ──>  BSP               App 调驱动，完全不知道有屏幕
ui    ──>  BSP               ui 只碰 board_config.h + i2c_bus.h（屏挂在 I2C0 上）
App   ✗    ui                互相看不见，中间只传 display_view_input_t 这一个结构体
```

```text
components/BSP/     硬件驱动，唯一直接碰总线与 GPIO 的一层
  board_config.h           ★ 全工程唯一引脚真源，改接线只改这一份
  I2C/i2c_bus.c ADC/adc_bus.c GPIO/gpio_util.c     总线封装、ADC 采样、WS2812 状态灯
  LED/led.c SERVO/servo.c BUZZER/buzzer.c          4 路灯(CH4~CH7) / 门舵机(CH0) / 蜂鸣器(CH3)
  KEY/key.c SENSOR/sensor.c                        按键消抖；温湿度+光照+雨滴，1000ms 采样，都带 valid
  I2S_MIC/i2s_mic.c VOICE/voice.c VOICE/voice_esp_sr.c   INMP441 采集 + ESP-SR 唤醒/命令词
components/App/     业务
  device_model.c          设备状态中枢：唯一状态真源 + 唯一硬件出口 + 开门级联
  app_cmd.h app_link.c    五个入口的唯一收敛点 home_command_execute()
  automation.c            ★ 零依赖叶子：模式 + 全部阈值 + NVS 落盘
  home_auto.c             两条规则：光照控灯、高温提示（含静音锁）
  ble_app.c               蓝牙：手机直连的收发 + 下发 WiFi（不依赖 WiFi/MQTT）
  net_link.c              WiFi STA 自动重连 + MQTT 客户端
  mqtt_protocol.c         topic 规划 + JSON 生成（带截断保护，蓝牙共用同一份）
components/ui/      屏幕
  panel.c                 SSD1306 驱动 + 1bpp 页显存 + 脏页差分
  panel_font.c            字库访问（271 汉字）+ UTF-8 解码
  display_view.c          四行排版 + 500ms 刷屏任务
main/               开机与串联
  main.c                  任务拓扑、语音指令翻译、按键语义、串口调试台
  board.c board.h         板级初始化编排 + 开机自检表
web/index.html      手机端控制面板（单文件）
```

> 文件名全都改过，**C 函数名一个都没改**：`bsp_led_set_power()`、`bsp_i2c_read()`、`home_ctrl_set_power()`、
> `auto_policy_is_auto()`、`net_proto_state_json()`、`home_command_execute()` 至今都是真名。
> 别照文件名猜函数名（`components/BSP/ADC/adc_bus.c` 里是 `bsp_adc_*`）。

## 二、五条命令入口，汇到一处

```text
语音(INMP441+ESP-SR) ─┐
板载按键 ─────────────┤
串口调试台 ───────────┼─> components/App/app_link.c  home_command_execute(dev, action, pct, src, detail)
手机蓝牙(App) ────────┤            │
网页面板(MQTT) ───────┘            └─> components/App/device_model.c  home_ctrl_set_*()
                                          └─> BSP 驱动（先动硬件）→ 成功才改软件状态
```

- 谁都不许自己再实现一遍规则。收敛到一个出口，五个入口行为天然一致，不会出现"语音开不了灯但手机能开"。
- **蓝牙和 MQTT 是两条平行的通道**：各自独立，谁断了都不影响另一个。蓝牙**完全不依赖 WiFi** ——
  这是本次改动的重点（客户不配网也能用手机控制）。
- 上行（板子 → 手机/网页）也共用一份 JSON：`components/App/mqtt_protocol.c` 生成一次，
  蓝牙和 MQTT 各发一份，所以两边看到的状态永远一致。协议见 [`蓝牙协议.md`](蓝牙协议.md)。
- **状态只存一份**，就在 `components/App/device_model.c` 里，别的文件不许自己再记一遍。
- 灯光在自动模式下会被拒，但不会闷着不吭声：语音回一句播报文本（没喇叭，以日志输出 `voice: 播报: <文本>`），MQTT 的 `ack` 里给同样的原因，两边是同一个字面量宏，免得解释不一致。
- **硬件写失败就不改软件状态**。否则手机显示"客厅灯已开"、物理上灯是灭的，人会去查灯查线，永远查不到是一次写失败。

## 三、任务表和主循环

| 任务 | 谁建的 | 周期 | 干什么 |
|---|---|---|---|
| `app_loop` | `main/main.c` | 500 ms | 自动联动 + 推屏 + MQTT 上报 + 状态灯 |
| `console` | `main/main.c` | 100 ms 超时 | 串口调试台，读一行执行一行 |
| `sensor_auto` | `components/BSP/SENSOR/sensor.c` | 1000 ms | 采三路传感器、更新快照 |
| `key_scan` | `components/BSP/KEY/key.c` | 10 ms | 按键扫描 + 消抖 + 短按/长按 |
| `voice_feed` / `voice_sr` | `components/BSP/VOICE/voice_esp_sr.c` | 事件驱动 | 喂麦克风音频 / 取帧 → 唤醒 → 命令词 |
| `view` | `components/ui/display_view.c` | 500 ms | 渲染 + 脏页差分推屏 |

语音那两个任务栈都是 **12288**、优先级 4、**都绑核 1**（核 0 留给 WiFi/LWIP）。栈必须这么大：
AFE 的 fetch 路径把 MultiNet7 的中间结果和 FFT 缓冲放在调用者栈上，8KB 实测会偶发溢出。

### 主循环 500ms 一轮，顺序有讲究

```c
bsp_sensors_get(&sn);  home_auto_tick(&sn);     // 1. 先跑联动：它可能改设备状态
build_view_input();    display_view_update();   // 2. 再推屏：拿到的是本轮最新状态
if (传感器攒够 2s) publish_sensor/weather();     // 3. 周期上报
if (状态变脏)     publish_state();              //    最多 200ms 合并一次，防抖
if (状态灯攒够 1s) bsp_status_led_show();        // 4. 状态灯很亮，不必跟 500ms
vTaskDelay(max(10, 500 - 本轮耗时));             // 5. 按实际耗时补偿，保持节拍
```

最后一行不能写死 `vTaskDelay(500)`：刷屏偶尔占十几毫秒，无脑延时会累积漂移，告警数字闪得没规律。

## 四、真机踩过的坑（这段最值钱）

- **I2C 只能跑 100kHz**。上 400kHz 推整页显存会超时，现象是屏"初始化成功却不显示"。
- **LEDC 通道是全局 8 个**，不是"每个定时器各有一套"，必须错开：**CH0 舵机 / CH3 无源蜂鸣器 / CH4~CH7 四路灯**。
- `ledc_channel_config()` **不做通道占用检查**：重复配同一通道会静默改挂定时器、旧引脚不一定断开；配错了舵机被 5kHz 驱动（剧抖、发热、门失控），现场极难定位。
- 无源蜂鸣器**不能蹭舵机的定时器**：LEDC 通道没有独立频率寄存器，频率只能跟定时器走；挂 50Hz 发不出 2kHz，改定时器频率又会把舵机的 20ms 周期一起毁掉 —— 所以单独用 `TIMER_1`@2kHz。
- **温度阈值 32.0℃ 开、31.5℃ 停**，必须留这 0.5℃ 死区，否则温度在 32 附近抖，蜂鸣器会响-停-响-停。
- **传感器 `valid=false` 时绝不动作**：悬空 ADC 会飘到任意值，而且是**看着合理的假值**，拿去开灯报警就成了"没人碰它，灯自己乱亮、蜂鸣器半夜响"。联动、显示、上报都要先看 `valid`；雨滴不可信时必须强制 `raining=false`，否则屏上一直卡在 `Raining!`。
- **开门级联点亮的客厅灯要给 30 秒免打扰**，否则规则1 会在 1 秒后按"光照够亮"把它关掉（真机日志见过 `AUTO: 光照 79.0% > 45.0% → 关客厅灯`）。这是全工程唯一一处"执行流向规则"的调用。
- **静音锁是"状态锁"，不是一次性动作**：只置 `buzzer=false` 没用，500ms 后温度还高规则立刻又开。用 `muted` 状态位锁住（`auto_policy_mute_buzzer()`），期间永不响；温度真的降到 31.5℃ 以下才 `auto_policy_clear_mute()` 解锁。语音"关蜂鸣器"只关听觉那一半，屏幕数字闪烁照旧。
- **开门亮灯只在"关 → 开"这一沿**，反复说"开门"不会反复动灯；来源标成 `SRC_AUTO`（不触发 3 秒手动保护期，也不被"自动模式拒绝灯光"拦下）；代码必须写在 `device_model.c`，写进 `main.c` 就变成"手机开门、按键开门都不亮灯"。
- **按键长按是每 500ms 重复上报的**，长按动作必须加"只执行一次"的锁，否则按住 KEY2 门会开-关-开-关反复翻转（舵机堵转发热）。
- **配件缺失只告警不崩**：`board_init()` 永远返回 `ESP_OK`，每项结果只记进自检表打一行日志。配件是分批到的，缺屏幕或缺温湿度时，WiFi / MQTT / 串口调试台 / 其它外设必须照常跑。

## 五、NVS 存了什么

两块：

```text
命名空间 sh_auto    键 cfg          模式 + 全部阈值 + 蜂鸣器极性（一个 auto_cfg_t）
命名空间 wifi_cfg   键 ssid / pass  手机 App 通过蓝牙下发的 WiFi 账号
```

- 阈值一改立刻落盘，掉电不丢。
- 读的时候 magic(`0x53484131`) + version + size + 数值体检（`cfg_sane`）四道校验，任一不过就丢回默认值。
- 结构体改了必须 `AUTO_CFG_VERSION + 1`，旧数据会被正确丢弃，而不是读出错位的脏值。
- `nvs_flash_init()` 要处理 `ESP_ERR_NVS_NO_FREE_PAGES` 与 `ESP_ERR_NVS_NEW_VERSION_FOUND`（擦除后重试一次），否则会"第一次烧录正常、改了分区表就无限重启"。
- **静音锁不持久化**：重启回到"没静音"—— 报警器重启就该恢复报警能力。
- **WiFi 优先用 `wifi_cfg` 那份**（客户在 App 里填的），没有才退回编译时的 `CONFIG_APP_WIFI_SSID`。
  这样客户换路由器不用重新烧固件，也不用装 ESP-IDF。

## 六、构建与工具

- `tools/build/build.ps1` —— 一键构建 / 烧录 / 监视；检测到中文路径会**自动镜像到纯 ASCII 目录**再构建（ESP-IDF 在 Windows 上不认中文路径）。
- `tools/build/wait_sources.ps1` —— 等所有源文件就位后自动构建（并行开发收口用）。
- `tools/dev/gen_panel_font.ps1`、`tools/dev/convert_font.py` —— 字库生成（GDI+ SimHei 17pt）与格式转换。
- `tools/verify/*` —— 脚本语法、注释、传感器、语音词表、MQTT、屏自检等一批检查，`.ps1` 随时可复检。

> ⚠ 本工程所有 `.ps1` **必须是 UTF-8 with BOM**：Windows PowerShell 5.1 会把无 BOM 的 UTF-8 按 GBK 解析，中文字面量会被破坏甚至语法报错。

## 七、两个刻意留下的间接层（别改成直接 include）

- `automation.c` 故意不依赖任何业务包，执行器要问"现在是不是自动模式"就问它：模式和阈值在全工程只有一份存储，不用"两边各存一份、初始化时同步" —— 漏同步一次就会出现"手机改了阈值、执行器还按旧值判断"。
- 开门联动靠回调槽转给 `home_auto.c`（`auto_policy_set_door_light_hook()` → `auto_policy_notify_door_lit()`），避免两个文件互相 include。`automation.c` 只管"存值 + 转告"，永远不主动碰硬件。

回调都在**调用者任务**里同步执行，所以回调里只许做轻量动作（置标志、发队列），不许阻塞 —— 等 MQTT、刷屏、延时都不行。
