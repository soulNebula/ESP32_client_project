# 蓝牙协议 · ESP32-S3 智能家居

> 手机 App 直连板子的通道。**客户只要装 App + 开蓝牙，不用串口、不用装 ESP-IDF、不用配 broker。**
> WiFi 账号也走这条通道下发（帧类型 `0x04`），所以网页面板同样不需要串口。

## 广播

```text
设备名      SmartHome-4d3b9c        ← <前缀>-<UID>；UID = MAC 后 3 字节，6 位小写十六进制
Service    5a1c0001-1e2f-4a3b-9c4d-5e6f708192a3
```

前缀在 menuconfig 里改（`智能家居 → 蓝牙设置 → 广播名前缀`），默认 `SmartHome`。
手机端按 Service UUID 过滤扫描，比按名字找稳。

## 三个 UUID

```text
Service   5a1c0001-1e2f-4a3b-9c4d-5e6f708192a3
RX        5a1c0002-1e2f-4a3b-9c4d-5e6f708192a3     手机 → 板子   write（带响应）
TX        5a1c0003-1e2f-4a3b-9c4d-5e6f708192a3     板子 → 手机   notify
```

连上之后**必须先订阅 TX 的 notify**，否则收不到任何数据。

## 帧格式

两个方向一样，都是 `[类型][数据分片]`：

```text
第 0 字节   type
            bit7 = 1  → 后面还有分片，这一帧没传完
            bit6~0    → 帧类型
第 1 字节起 数据分片（UTF-8，一般就是 JSON）
```

- 一个分片最长 = 协商出来的 MTU − 3（ATT 每包占 3 字节头）。
  板子侧优先 **512**（NimBLE 上限），手机侧申请 **517**（Android 上限），最终取两边较小的那个 —— 正常是 512。
  手机只给 247 或默认 23 也得能用 —— 所以**必须支持分片重组**。
- 接收方按 `type` 累积，直到收到 bit7 = 0 的那一片，才算一帧收完。
- 重组上限 **1024 字节**，超了丢掉并记日志（正常最大的是 config，约 300 字节）。

## 下行帧（手机 → 板子）

```text
0x01  CMD     数据 = 和 MQTT 的 <base>/cmd 一模一样
              三种写法都认：{"dev":"led_living","action":"on"}
                            dev=led_living,action=on
                            led_living_on
0x02  CONFIG  数据 = 和 MQTT 改阈值一模一样 {"dev":"config","action":"<键>","value":<值>}
              键名见 MQTT协议.md 那张表（buzzer_on_c 是 ℃ 整数，32 就是 32℃）
              ★ 数值键（light_on_pct / buzzer_on_c / temp_alert_c / rain_pct …）发整数
              ★ 布尔键（auto_light_enable / auto_buzzer_enable / door_light_cascade /
                buzzer_active_low）必须发 JSON 的 true / false，**别发字符串 "false"** ——
                字符串走不通会掉进兜底分支变成 "1"，反而开了
0x03  GET     数据忽略 → 板子立刻回 0x11 + 0x12 + 0x13 + 0x14 四帧
0x04  WIFI    数据 = {"ssid":"我家WiFi","pass":"密码"}
              → 存 NVS 并立刻重连；**这是客户唯一需要配的东西，不用串口**
              传空 ssid 表示清除，回到编译时的默认值
0x05  PING    数据忽略 → 板子回 0x16 INFO
```

## 上行帧（板子 → 手机）

数据内容**和 MQTT 对应 topic 的 JSON 逐字一样**，所以解析代码两边可以共用。

```text
0x11  STATE    = MQTT <base>/state        设备开关 / 模式 / wifi / ip / rssi
0x12  SENSOR   = MQTT <base>/sensor       温湿度 / 光照 / 雨滴（2 秒一次）
0x13  WEATHER  = MQTT <base>/weather      天气卡片
0x14  CONFIG   = MQTT <base>/config       当前阈值和模式
0x15  ACK      = MQTT <base>/ack          指令结果，失败原因在 detail
0x16  INFO     = {"name":"SmartHome-4d3b9c","ver":"1.0.0","base":"smarthome/4d3b9c","ble_mtu":512}
                 base 就是网页面板要填的那串，App 里直接显示给客户抄
```

`INFO` 是给客户省事的：装上 App 连上就能看到 base，**不用再去翻串口日志**。
（板子的控制台其实还在，但那是给自己排查用的，客户流程不需要它。）

## 出错怎么办

- 数据解析失败 → 回 `0x15 ACK`，`ok:false`，`detail` 写清原因（和 MQTT 的 ack 同一套文案）
- 收到不认识的帧类型 → 忽略 + 打日志，不断连接
- 没连上时板子照常跑：蓝牙、MQTT、网页三条通道各自独立，谁断了都不影响另外两个
- 断线重连后，App 重新订阅一次 TX，并发一帧 `0x03 GET` 把状态拉全

## 板子端怎么发

蓝牙和 MQTT 共用同一份 JSON 生成代码（`components/App/mqtt_protocol.c`），
所以**两边内容永远一致**，不会出现"手机看到灯开着、网页看到灯关着"。

## Android 侧要点

- 需要权限：Android 12+ 用 `BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT`（`neverForLocation`）；
  11 及以下用 `BLUETOOTH` + `BLUETOOTH_ADMIN` + `ACCESS_FINE_LOCATION`
- 扫描时按 Service UUID 过滤；`BluetoothLeScanner.startScan(filters, ...)`
- 连上后 `requestMtu(517)`，再 `discoverServices()`，找到 TX 后
  `setCharacteristicNotification(true)` + 写 CCCD 描述符（`0x2902`）开启通知
- 写 RX 用 `WRITE_TYPE_DEFAULT`；超过 MTU−3 时按上面的分片规则自己切
- 别用第三方蓝牙库（和现在不引第三方 MQTT 库一个道理）
